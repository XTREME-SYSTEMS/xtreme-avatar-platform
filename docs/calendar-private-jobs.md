# Private Calendar job data and files

Prepared 2026-11-07. Source work began from app revision `7ab348cb9aa62ef949dd4a3d35bab64ffcee4ae4`. This is a creator-private feature in the existing app, Edge API and Storage project. It does not add a queue, runtime, public file store or shared Google event attachments.

## Contracts and ownership

The machine-readable route contract is `docs/calendar-job-contract.json`. Existing `work_hub_v1` jobs remain canonical: optional jobId must exist in the same member's saved WorkHub when linked. No project is silently copied or created. Per-event client, location, stage and notes are stored in the existing private_state table at key `calendar_job_v1:<eventRef>`, with optimistic version checks. Google descriptions, attendees and other private event content are not copied by default.

Every route verifies app cookies in Next, verifies the bearer independently in Edge, checks active membership and the account header, and obtains current Google binding through the parent-owned `resolveCalendarBinding` helper. The browser supplies eventId and a positive connection revision, never an owner, storage path or eventRef. The runtime derives eventRef from the app user, verified Google subject, primary calendar and event ID; it survives same-account reconsent and key rotation. Reconnecting a different Google account does not alias the original event binding.

Private reads that await Storage repeat the Google binding check before returning, followed by current membership and manifest checks. The Edge preserves cancellation. Private job/file work uses a shared 100-second context/Storage signal, a 110-second Next upstream timeout and 120-second Next route limit; existing Google Calendar route budgets are unchanged.

## Additive database migration

Generated with local Supabase CLI 3.0.0 after checking its help:
`supabase/migrations/20261107201240_calendar_private_files.sql`.

The migration adds only `xtreme_avatar.job_attachments`, its index, private read RLS, a trusted lifecycle function and one bucket-specific restrictive Storage policy. It does not change existing private state, jobs, public assets or other product tables.

Authenticated users can select their own manifest only while active in its organization. They cannot insert/update/delete a manifest or execute the trusted function. Thus Data API callers cannot forge a ready status, MIME type, hash, owner or object path. The Edge uses a fixed reviewed DB adapter method to invoke `xtreme_avatar_private.file_mutation` through the existing server DB connection; function names and SQL are never caller-controlled. The function uses an empty search_path, rechecks confirmed active identity, and serializes each user's quota/lifecycle work with a transaction advisory lock. Ordinary DB operations still use transaction-local authenticated role and RLS.

The object path is generated by the server as organization/user/eventRef/fileUUID.extension. Existing paths are never overwritten or reassigned. A request UUID is idempotent only for the same organization, event, project reference and file metadata.

## File lifecycle and limits

Files are at most 4,000,000 bytes, below Vercel's documented 4.5 MB function payload limit. Limits are ten active files per event and 200,000,000 bytes per user across events; pending/unknown uploads remain counted.

Reserve → claim → stored bytes → ready is durable. Byte signatures and declared size must agree before upload. SHA-256 is saved with the claim, confirmed before ready, and rechecked on download. Ready replay must supply the same bytes, not merely the same file ID. A lost upload response can be reconciled by checking the already stored object's size, signature and hash; this never sends the file again.

An uploading row is never deletable solely because a timeout/lease expired. Unknown provider outcomes retain custody and quota until confirmed. If no object can be confirmed, the row remains visibly pending and may need an operator to establish a definitive provider outcome; the app does not pretend deletion succeeded. Explicit file removal uses version/confirmation checks and a deleting tombstone; an uncertain deletion is retried only by the user's explicit action. No automatic upload, delete or quota release follows a network error.

## Safe rendering boundary

The backend signature check is not an antivirus scanner or a full image decoder. Every raw file is served with Content-Disposition attachment, nosniff, private/no-store and sandboxed/no-source CSP. PDFs are always downloads. There are no signed URLs or public object URLs. SVG, HTML and other active MIME types are not accepted.

The approved frontend may decode supported images into a dimension/pixel/byte-bounded canvas preview. It must not embed raw documents or treat a signature match as a successful full image decode. Corrupt or unsupported images receive an honest no-preview fallback. Files are creator-private; none are automatically shared with event attendees or WorkHub folders.
